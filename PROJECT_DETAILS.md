# Project 4: Reliable Transport Protocol

**This project is due at 11:59pm on March 17, 2026.**

## Description

You will design a simple transport protocol that provides reliable datagram service. Your protocol will be responsible for ensuring data is delivered in order, without duplicates, missing data, or errors. Since the local area networks at Northeastern are far too reliable to be interesting, we will provide you with access to a virtual environment that will emulate an unreliable network.

For the assignment, you will write code that will transfer a file reliably between two nodes (a sender and a receiver). You may assume that the receiver is run first and will wait indefinitely, and the sender can just send the data to the receiver.

---

## Your Programs

For this project, you will submit two programs: a sending program **4700send** that accepts data and sends it across the network, and a receiving program **4700recv** that receives data and prints it out in-order. You must use **UDP** as the transport protocol. You may not use any other transport protocol libraries in your project (such as TCP). You must construct the packets and acknowledgements yourself, and interpret the incoming packets yourself.

### Requirements

- **You have to design your own packet format** and use UDP as the transport layer protocol. Your packet might include fields for packet type, acknowledgement number, advertised window, data, etc. This part of the assignment is entirely up to you.

Your code **must** do the following:

- The sender must accept data from **STDIN**, sending data until **EOF** is reached
- The sender and receiver must work together to transmit the data reliably
- The receiver must print out the received data to **STDOUT** in order and without errors
- The sender and receiver must print out specified debugging messages to **STDERR**
- Your sender and receiver must **gracefully exit**
- Your code must be able to transfer a file with any number of packets dropped, duplicated, and delayed, and under a variety of different available bandwidths and link latencies
- Your sending program must be named **4700send** and your receiving program must be named **4700recv**
- You must also submit a **Makefile** that builds your client program; if you do not need to do so, you must submit a Makefile with a blank target (e.g., `all:`)
- **Datagrams** generated by your programs must each contain **less than or equal to 1500 bytes** of data. Any datagrams sent with more data than that will be dropped.

You may implement any reliability algorithm(s) you choose. However, more sophisticated algorithms (i.e., those that perform better) will be given higher credit. Desirable properties include (but are not limited to):

- **Fast:** Require little time to transfer a file.
- **Low overhead:** Require low data volume to be exchanged over the network, including data bytes, headers, retransmissions, acknowledgements, etc.

Regardless, **correctness matters most**; performance is a secondary concern. Your code should check the integrity of every packet received. We will test your code by reordering packets, duplicating packets, delaying packets, and dropping packets; you should handle these errors gracefully, recover, and never crash nor print out data at the receiver that is different than what was sent at the sender.

### Language

You can write your code in whatever language you choose, as long as your code compiles and runs on Gradescope. Your code must compile and run on the command line. You may use IDEs during development, but do not turn in your project without a Makefile. Make sure your code has **no dependencies** on your IDE. Starter code is provided in Python and Java; you may use either, or port the starter code to another language yourself.

## Testing Environment

The goal is to develop a TCP-like, reliable transport protocol. A **simulator** is provided that emulates unreliable networks (slow, lossy, reordering, duplication). The simulator interposes itself on your connection and emulates delay, router buffers, and various forms of network unreliability.

### Starter code

Very basic starter code (Python and Java) implements a simple stop-and-wait protocol. You may use this as a basis or create a new repo from the template.

### Simulator

- The simulator is implemented in a script named **run** (part of the starter code).
- **Do not modify `run`.** Grading uses the original `run` and `configs/`.
- Configuration files in **configs/** define the situations your code must handle (same configs used for evaluation, plus additional hidden ones).
- You do **not** need to parse the configuration files; the simulator does that.

**Command line:**

```bash
$ ./run <config-file>
```

The simulator will read the config file, start your sender and receiver with the appropriate arguments, feed your sender data, record the receiver’s output, and compare it to the expected output. It will report pass/fail and a summary of any error.

## Program Specification

### Sender: 4700send

**Syntax:**

```bash
$ ./4700send <recv_host> <recv_port>
```

- **recv_host** (Required): Domain name (e.g., "foo.com") or IP address (e.g., "1.2.3.4") of the remote host
- **recv_port** (Required): UDP port of the remote host

- The sender must open a UDP socket and send packets to the given IP address and port.
- Data to transmit must be supplied via **STDIN**. The sender must read from STDIN and send to the receiver via the UDP socket. You may assume **4700recv** is already running on the remote host/port (no connection setup required).
- Debug output may go to **STDERR** only.

**NOTE:** **4700send** must **exit** once it has determined that all data has been successfully received by the receiver. This exit is the signal the simulator uses that the test is over.

### Receiver: 4700recv

**Syntax:**

```bash
$ ./4700recv
```

- On startup, the receiver must bind to a UDP port.
- The **first** thing it prints to **STDERR** must be:
  ```text
  Bound to port <port>
  ```
  where `<port>` is the local UDP port number it chose.
- It then waits for datagrams from the sender. Any other debug messages must go to **STDERR**.
- The receiver must print **only** the received data from the sender to **STDOUT**. The data must be **identical** to what was supplied to the sender via STDIN (no missing, reordered, or bit-level errors).

**NOTE:** **4700recv** should **not** exit on its own, even after it believes all data has been received. The simulator will kill it when **4700send** exits.

## Implementation Strategy

Handle errors (lost, duplicate, corrupted, delayed packets) and adapt to different bandwidths, latencies, and jitter. Implement in stages; the configs roughly follow these levels:

| Level | What to implement |
|-------|-------------------|
| **1** | **Larger window:** More than one packet in flight. Window of **two** packets is enough for level 1. (Larger windows may cause drops and failures at this level.) |
| **2** | **Duplicate detection:** Use **sequence numbers** to detect duplicate packets/acks and **avoid printing duplicates** at the receiver. Window still ~2 for level 2. |
| **3** | **Reordering:** Network delay is variable; packets may arrive out of order. Implement a **receiver window** (buffer) so you can hold out-of-order packets and deliver in order. Sender window of **at least four** packets. |
| **4** | **Packet loss:** Network drops packets. Implement **loss detection** at the sender and **retransmit** lost packets. Use a rule of thumb that RTT is about **1 second**. |
| **5** | **Corruption:** Network corrupts packets. **Detect corruption** and drop bad packets (treat as lost). Do this for **both** data and ack packets (sender and receiver). **NOTE:** Required only for CS 5700. |
| **6** | **Variable latency:** Configs use different latencies. **Estimate RTT** at the sender and set timeouts accordingly (e.g., about **twice the RTT**). |
| **7** | **Variable bandwidth:** Configs use different bandwidths. **Adjust sender window size** based on observed delivery (grow and shrink as needed). |
| **8** | **Stress tests:** Multiple faults at once. If levels 1–7 are correct, these should pass. |
